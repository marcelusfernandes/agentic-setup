## 2. Notas por repositório (com paths lidos)

### `anthropics/claude-code` (mono-repo oficial)
- Tem `plugins/` na raiz com 13+ plugins oficiais: `plugins/hookify/`, `plugins/security-guidance/`, `plugins/pr-review-toolkit/`, `plugins/code-review/`, `plugins/feature-dev/`, `plugins/commit-commands/`, `plugins/ralph-wiggum/`, etc. (`gh api repos/anthropics/claude-code/contents/plugins`).
- `plugins/hookify/hooks/hooks.json` + `pretooluse.py/posttooluse.py/stop.py/userpromptsubmit.py`: Python puro, **sempre `sys.exit(0)`** mesmo em erro de import — **fail-open explícito e documentado no código** ("ALWAYS exit 0 - never block operations due to hook errors").
- `plugins/security-guidance/hooks/hooks.json` + `sg-python.sh`: o shim bash tenta `python3` → `python` → `py -3`, cada um testado com `-c ""` antes de usar (contorna o stub da Microsoft Store no Windows que "exit 49 silenciosamente"). Se nenhum funcionar, **falha fechado com mensagem clara e `exit 1`** — mas isso só derruba aquele hook específico, o resto da sessão continua. `ensure_agent_sdk.py` cria um venv em `~/.claude/security/agent-sdk-venv` sob demanda para instalar `claude_agent_sdk` (dependência para a revisão via LLM) — ou seja, mesmo o exemplo "oficial mais robusto" acaba **puxando um venv Python + pip install** na hora.
- `pr-review-toolkit`, `code-review`, `feature-dev`, `commit-commands` = **sem `hooks/`**, só `agents/` + `commands/` (confirmado via listagem de diretório). `pr-review-toolkit/agents/` tem 6 agentes especializados (`code-reviewer`, `code-simplifier`, `comment-analyzer`, `pr-test-analyzer`, `silent-failure-hunter`, `type-design-analyzer`) e um único `commands/review-pr.md` que os orquestra — toda a etapa de "review" do loop pedido pela tarefa é, na implementação oficial da própria Anthropic, **prompt multi-agente, não hook**.
- `anthropics/claude-plugins-official` é outro repo (separado do claude-code), majoritariamente **wrappers de MCP para serviços externos** (Asana, Discord, GitHub, GitLab, Linear, Firebase...) — não achei hooks de workflow git ali; tem pipeline de CI próprio (`.github/workflows/validate-plugins.yml`, `scan-plugins.yml`) para validar plugins submetidos por terceiros em `external_plugins/`.
- `.github/` do `claude-code` **não tem `PULL_REQUEST_TEMPLATE.md`** (confirmado: 404 em `gh api repos/anthropics/claude-code/contents/.github/PULL_REQUEST_TEMPLATE.md`), só `ISSUE_TEMPLATE/*.yml` em formato "Forms" moderno (`bug_report.yml`: `body: [{type: markdown|checkboxes|textarea}]`). O loop issue→PR do próprio repo roda via `.github/workflows/claude.yml`, que dispara `anthropics/claude-code-action@v1` quando alguém menciona `@claude` em issue/PR/comentário/review — **não é um hook local do Claude Code**, é uma GitHub Action.

- `docs/features/hooks-declare-their-crash-policy.md`, `docs/how-to/declare-a-hook-crash-policy.md`, `docs/adr/0004-worktree-workstream-seam-module.md`: documentação formal (ADR) do design de fail-open/closed explícito — não encontrei nada parecido em nenhum outro repo pesquisado.

## 3. Fatos confirmados na documentação oficial

Fonte: `https://code.claude.com/docs/en/hooks` (redirecionado de `docs.claude.com/en/docs/claude-code/hooks`), `https://code.claude.com/docs/en/plugins-reference`, `https://code.claude.com/docs/en/permissions`.

**Eventos de hook** — a lista é bem maior do que os 8-9 "clássicos" (PreToolUse/PostToolUse/Stop/etc.) documentados nos tutoriais mais antigos; a doc atual lista ~30 eventos, incluindo `PostToolBatch`, `PermissionDenied`, `TeammateIdle`, `WorktreeCreate`/`WorktreeRemove`, `PreModelSwitch`/`PostModelSwitch`, `InstructionsLoaded`, `ConfigChange`, `Elicitation`. Isso é relevante para o boilerplate: dá pra reagir a `WorktreeCreate`/`WorktreeRemove` nativamente em vez de reimplementar detecção de worktree em bash (como `superpowers` faz manualmente).

**Payload JSON via stdin** — campos comuns a todos os eventos: `session_id`, `prompt_id`, `transcript_path`, `cwd`, `permission_mode`, `effort.level`, `hook_event_name`. Em subagentes: `agent_id`, `agent_type`. Em eventos de tool: `tool_name`, `tool_input` (formato varia por ferramenta — Bash tem `command`/`description`/`timeout`/`run_in_background`; Edit/Write têm `file_path`), `tool_use_id`. **Não há confirmação de que `tool_input.command` também seja exposto como variável de ambiente `$TOOL_INPUT`** — os exemplos oficiais sempre usam stdin + `jq`/`json`.

**Exit codes**: `0` = sucesso (stdout tratado como contexto ou JSON, dependendo do evento); `2` = **sempre bloqueia**, independente de qualquer JSON emitido (vence qualquer outra decisão); qualquer outro código = erro não-bloqueante na maioria dos eventos, exceto `WorktreeCreate`, que aborta em **qualquer** código não-zero. Timeouts: 600s padrão para hooks de comando/http/mcp_tool, 30s para `prompt`, 60s para `agent`, encurtado para 30s em `UserPromptSubmit`/`PreModelSwitch`/`PostModelSwitch`.

**JSON de saída avançado**: `hookSpecificOutput.permissionDecision` (`allow`/`deny`/`escalate`) + `permissionDecisionReason` é o mecanismo recomendado para `PreToolUse` (em vez de `exit 2`, que não deixa passar uma razão customizada tão rica). `updatedInput` permite ao hook **reescrever** o `tool_input` antes da execução. `continue`/`stopReason` em `Stop`/`SubagentStop` força o agente a continuar.

**Plugins**: manifest em `.claude-plugin/plugin.json` (só `name` é obrigatório); hooks em `hooks/hooks.json` (ou inline em `plugin.json` via campo `"hooks"` apontando pro arquivo). `${CLAUDE_PLUGIN_ROOT}` é uma env var exportada para o processo do hook (e para MCP/LSP subprocesses) apontando para o diretório de instalação do plugin — **confirmado** oficialmente, inclusive com a recomendação de sempre usar aspas (`"${CLAUDE_PLUGIN_ROOT}"/script.sh`). Existe também `${CLAUDE_PLUGIN_DATA}` (dir persistente entre updates) e `${CLAUDE_PROJECT_DIR}` (raiz do projeto, não do plugin). Tipos de hook: `command`, `http`, `mcp_tool`, `prompt`, `agent` — os dois últimos rodam avaliação via LLM/agente, não script.

**`permissions.deny` / `permissions.allow` (Bash)** — esta é a parte mais valiosa para o objetivo do boilerplate:
- Sintaxe `Bash(git push *)`: o `*` fica **depois** do subcomando que importa; `Bash(git * main)` e `Bash(git push *)` **não** são a mesma coisa — o primeiro libera *qualquer* subcomando terminando em `main` (perigoso, inclui `-c core.fsmonitor=<script>`).
- `Bash(comando *)` com espaço antes do `*` também casa a forma "nua" (`Bash(ls *)` casa `ls` sozinho); `Bash(comando*)` sem espaço é diferente (casa `lsof` também). `:*` no final é equivalente ao `<espaço>*`.
- Claude Code **conhece operadores de shell** (`&&`, `||`, `;`, `|`, `|&`, `&`, newline) e casa `deny`/`ask` em **qualquer subcomando**, inclusive dentro de subshell, `$(...)` ou corpo de `for` — então um `deny` para `git push --force` bloqueia mesmo escondido atrás de `cd /tmp && ... && git push --force`.
- Antes de casar, o Code **remove wrappers conhecidos** (`timeout`, `time`, `nice`, `nohup`, `stdbuf`, `command`, `builtin`, `noglob` do zsh) — então uma regra escrita para `npm test` também gruda em `timeout 30 npm test`. Só remove atribuição de env var líder para regras de **allow** (regra de `deny`/`ask` casa mesmo com `FOO=bar` na frente).
- **Limitação documentada explicitamente**: não dá pra restringir por conteúdo arbitrário de argumento (ex.: `Bash(curl http://github.com/ *)` não impede variações de URL) — a doc recomenda combinar com CLAUDE.md (não é enforcement) ou sandboxing.
- **Não dá pra escrever `Bash(command:rm *)`** mirando só o campo `command` — Claude Code ignora essa forma e emite warning de startup, porque seria contornável por comando composto.
- Ferramentas como `devbox run`, `direnv exec`, `mise exec`, `npx`, `docker exec` **não** estão na lista de wrappers removidos, então uma regra de allow tipo `Bash(devbox run *)` libera *qualquer coisa* depois do `run` (inclusive `devbox run rm -rf .`) — é preciso escrever regra específica por comando interno.
- Ou seja: dá para bloquear **declarativamente, sem nenhum código**, os casos "nunca force-push" (`Bash(git push *--force*)` em deny, como o próprio `davila7` faz) e "nunca reset --hard"/"nunca rm -rf" (prefixo fixo). Mas **"nunca dar push na main"** já não dá pra fazer só com pattern de comando — como o hook `prevent-direct-push.py` do davila7 mostra, isso depende do **branch atual**, que só um script consegue checar (`git branch --show-current`). Essa é a linha divisória real entre "regra declarativa" e "precisa de script".

## 4. Padrão menos complexo que ainda é agnóstico (recomendação)

**Runtime do hook: Bash + `printf`/`grep`, sem `jq` nem Python, como padrão.** É o que `obra/superpowers` faz para o único hook que de fato precisa rodar em toda máquina (`SessionStart`), e é o que dá menos superfície de falha: bash já está presente em qualquer Mac/Linux, e o custo real fica só no Windows (resolvido com o padrão polyglot `.cmd`/bash do superpowers, que **falha aberto silenciosamente** se não achar `bash.exe`). Reservar Python só para as regras que **precisam** de estado externo (branch atual, diff, etc.) que dá trabalho reproduzir em bash puro — e, quando usar Python, seguir o padrão da Anthropic (`sg-python.sh`: sonda `python3`→`python`→`py -3` com `-c ""`, nunca assumir que `python3` existe) em vez do padrão do `disler` (`uv run --script`), que amarra o usuário a instalar `uv` — uma dependência a mais sem necessidade real, já que nenhuma das libs usadas ali (regex, json, subprocess) precisa de um resolvedor de pacotes por chamada de hook.

**Parsing: nunca `jq`.** Nenhum dos exemplos oficiais da própria Anthropic (`hookify`, `security-guidance`) usa `jq` — ambos leem `json.load(sys.stdin)` em Python quando precisam de parsing estruturado, e o único exemplo 100% bash oficial (`superpowers/session-start`) evita JSON parsing completamente porque só *produz* JSON (nunca precisa *consumir* o payload de entrada). Isso é uma pista forte: **se o hook só precisa decidir com base no texto do comando, `grep -E`/`case` em bash bastam e nem chegam a precisar de parsing de JSON**; só quando o hook precisa ler `tool_input.file_path` ou campos aninhados é que vale trocar para Python com `json` da stdlib. `jq` aparece só nos exemplos didáticos da própria doc oficial (não nos plugins reais que a Anthropic distribui) — é aceitável como referência de doc, mas adiciona uma dependência de sistema (`jq` binário) que nem `bash` nem `python3` exigem.

**Config por projeto: não crie um arquivo de config dedicado.** Nenhum dos 8 repositórios pesquisados usa um arquivo de manifesto tipo `.agentic-workflow.yml` para declarar comando de teste/lint/typecheck. Os dois padrões reais observados são: (a) **detecção heurística pelo agente** via instrução em prosa numa skill/CLAUDE.md ("rode `npm test`/`cargo test`/`pytest`/`go test ./...`, o que existir") — usado por `superpowers`, o mais popular do grupo; ou (b) **delegar para variável de ambiente** só quando o hook precisa rodar algo de forma determinística fora do controle do agente (`PROTECT_MCP_POLICY`, `SECURITY_GUIDANCE_DISABLE`). Para o boilerplate, a recomendação é (a): deixar a skill/CLAUDE.md instruir o agente a *descobrir* o comando de teste do projeto (lockfile/Makefile/`package.json#scripts`), e reservar hooks apenas para os guard-rails que **não podem** depender do agente lembrar de rodar (força-push, push em `main`, `--no-verify`).

**Distribuição: plugin oficial (`.claude-plugin/plugin.json` + `hooks/hooks.json`), não "copie estes arquivos".** Confirmado pela doc oficial que `${CLAUDE_PLUGIN_ROOT}` é suportado nativamente e exportado também para MCP/LSP subprocesses — isso resolve o problema de path que o `davila7` (modelo npx/copy-paste) e o `disler` (clone-como-template) empurram para o usuário resolver na mão. Um plugin com hooks é instalável via `claude plugin install` ou `--plugin-dir` local, versionável (`version` no manifest), e pode ser testado isoladamente (como fazem `superpowers/tests/hooks/` e `wshobson/agents/plugins/protect-mcp/test/`) sem exigir que o consumidor rode um instalador Node.

**Quanto dá pra fazer 100% declarativo, com `permissions.deny`, sem nenhum hook:** mais do que se imagina, mas não tudo. "Nunca force-push" e "nunca `git reset --hard`"/"nunca `rm -rf`" são só prefixo de comando — dá pra travar com `permissions.deny: ["Bash(git push *--force*)", "Bash(git push * -f *)", "Bash(git reset --hard*)", "Bash(rm -rf*)"]` no `.claude/settings.json`, **zero código**, exatamente o que `force-push-blocker.json` do davila7 mostra (o "hook" ali nem precisa ser hook — é um `echo` fixo, poderia virar regra `deny` pura). Isso cobre a maior parte dos "never" do pedido original. O que **não** dá pra declarar sem script é "nunca push direto na `main`", porque depende do estado do branch atual, não do texto do comando — isso exige um hook de fato (o `prevent-direct-push.py` do davila7, ou um equivalente em bash com `git branch --show-current`). Recomendação: usar `permissions.deny` declarativo para os casos de padrão-de-comando fixo, e reservar hooks em bash (não Python) apenas para as 1-2 regras que realmente precisam checar estado do repositório.

**"Review" e "merge gate" do loop: GitHub Actions + branch protection, não hook do Claude Code.** Em todos os lugares onde a própria Anthropic implementa a etapa de review (`plugins/pr-review-toolkit`, `plugins/code-review`, `plugins/feature-dev` — todos zero hooks, só `agents/*.md` + `commands/*.md` de prompt) e o gate de merge (`anthropics/claude-code-action` + `agent-approval-check`, que exige N aprovações humanas via branch protection e status check, documentado como "the same gate Anthropic runs internally on every agent-authored PR"), a decisão determinística fica na infraestrutura do GitHub (Actions, required status checks, branch protection), não em hooks locais do Claude Code. Para o boilerplate: implemente "nunca mergear PR de agente sem aprovação humana" como regra de branch protection + Action, não como hook — hooks locais do Claude Code não rodam no momento do merge (é um evento do GitHub, fora do processo do Claude Code), então tentar fazer esse gate como hook seria a ferramenta errada para o trabalho.

**Templates de issue/PR**: nenhum dos repositórios pesquisados (nem os dois oficiais da Anthropic) usa `PULL_REQUEST_TEMPLATE.md` — confirmado com 404 em `claude-code`, `claude-code-action`, `davila7/claude-code-templates` e `disler/claude-code-hooks-mastery`. `ISSUE_TEMPLATE/` existe nos dois repos oficiais, em dois formatos (Forms `.yml` em `claude-code`, clássico `.md` em `claude-code-action`). Para o boilerplate: vale incluir um `ISSUE_TEMPLATE` no formato Forms (mais moderno e validado no lado do GitHub), mas não há evidência de que um `PULL_REQUEST_TEMPLATE.md` preenchido à mão seja parte do padrão real — o fluxo de PR agêntico observado depende de status checks automatizados, não de descrição manual de PR.

**Consenso da comunidade, honestamente**: os projetos mais populares (superpowers 282k★, compound-engineering 24.9k★, VoltAgent 24.9k★) **não usam hooks para enforcement** — apostam quase tudo em skills/prosa para guiar o agente, e usam hooks só para injeção de contexto leve (`SessionStart`). Hooks de bloqueio pesado (Python com centenas/milhares de linhas, LLM review, Cedar policy engine) aparecem nos projetos que tratam "governança" como produto (`security-guidance` da própria Anthropic, `protect-mcp`/`review-agent-governance` do wshobson, `open-gsd/gsd-core` para worktree) — não são o padrão popular, são a exceção mais sofisticada. Isso **contraria a intuição inicial** de que "guard hooks" são o jeito canônico de impor regras: no ecossistema real, a maioria prefere confiar no agente + `permissions.deny` simples, reservando hooks de verdade para os poucos casos que dependem de estado externo. E busca dedicada por "worktree como padrão de hook" (`isolation: worktree`, `EnterWorktree`, "git worktree parallel claude agents") não achou nada além do próprio `gsd-core` e do orquestrador externo `smtg-ai/claude-squad` (8.433★, CLI em Go que envolve tmux + `git worktree` e spawna Claude Code como subprocesso — fora do ecossistema de hooks/plugin) — isolamento de worktree por agente, na prática, ou é feature nativa do harness (`isolation: "worktree"` no frontmatter de agente, confirmado em `plugins-reference`) ou é ferramenta externa; não é algo que a comunidade normalmente constrói via `hooks.json`.

**O que me surpreendeu**: (1) a quantidade de "hooks" no ecossistema que na verdade são **skills que ensinam a copiar um JSON pra `settings.json`**, não plugins que se auto-instalam (`block-no-verify` do wshobson); (2) o sistema "function hooks" do davila7 é **explicitamente experimental/não-oficial** (`anthropics/claude-code#91870`) mas está publicado e documentado como se fosse um recurso normal do produto — risco real de alguém copiar aquilo achando que é a API estável; (3) mesmo o exemplo "oficial" mais robusto (`security-guidance`) acaba montando um venv Python + instalando `claude_agent_sdk` via pip na hora, ou seja, nem a própria Anthropic escapa de puxar dependência de runtime quando o hook precisa fazer revisão via LLM; (4) `protect-mcp` delega a lógica do hook inteira para `npx pacote@versão`, um padrão que não vi documentado em lugar nenhum mas que resolve "distribuição de lógica" sem nenhum arquivo — trade-off é rede + confiança em binário de terceiro a cada chamada; (5) o único enforcement mecânico real de "escopo de escrita ⊆ worktree" que encontrei (`gsd-worktree-path-guard.js`) documenta, no próprio código, a razão exata pela qual instrução em prosa não basta: *"the prose guard in agents/gsd-executor.md step 0b is never enforced because the model under load skips it"* — uma confirmação direta, em produção, do motivo pelo qual "nunca" precisa ser hook ou `permissions.deny`, não CLAUDE.md; (6) nem a Anthropic usa hook para o gate de merge de PR de agente — usa branch protection + status check do GitHub (`agent-approval-check`), documentado como "the same gate Anthropic runs internally on every agent-authored PR".

**Não verificado** (fui explícito no texto onde isso apareceu): a forma `"hook": {...}` (singular) e a leitura de `$TOOL_INPUT` como env var, usadas no snippet do `block-no-verify` do wshobson, não batem com o schema confirmado na doc oficial (`"hooks": [...]` no plural, payload via stdin) — não consegui confirmar se é uma sintaxe alternativa válida ou um erro no repo comunitário.
